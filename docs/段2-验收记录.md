## 1. 协议层怎么测的(★ 本验收器最重要的一个决定)

企微的协议是**逆向得来的**(无公开文档),而真实凭据不在本机。朴素做法是把
`BotClient` mock 掉 —— 但那样测的是 mock,不是协议。

段2 的验收器改用 **`FakeWeComServer`**:用 `websockets` 起一个**真 WebSocket 服务端**,
**逐字节**按 `domains/bot/protocol.py` 的帧格式收发(`aibot_subscribe` / `ping` /
`aibot_send_msg` / 三步素材上传 …),并可编程注入故障(不回 ping、回 `errcode=500`、
延迟回执)。

于是下面这些**全部走真实代码路径**:

* 帧编解码、`req_id` 三段格式、控制字符过滤;
* **ack 按 `req_id` 唤醒** + **迟到回执静默忽略**;
* `_send_only`(回复不等 ack);
* **心跳连丢 2 次判死 → 强断 → 指数退避重连**;
* 三步素材上传的**真实分片**(>512KB → 2 片);
* `asyncio.Queue` 派发、**机器人级限频的真实时间戳**、重试退避、审计落库。

**唯一标 BLOCKED 的是 V21 的"真实企微服务器是否接受这套帧"** —— 需要
`core_bots` 里的真凭据 + 外网。这一条**不许伪造成 PASS**。

> 共 **13 条**(4.1–4.11 + 4.13 + 4.14;后两条分别由交付后评审与用户提问触发),
> 另有 2 条实测确认无问题的行为留证(4.12)。

### 4.1 `Runtime.create(...).__aenter__()` 不保活 → GC 触发 `aclose()`(🔴 验收器自身)

`Runtime.create` 是 `@asynccontextmanager`。写成
`return await Runtime.create(...).__aenter__()` 时,那个 async generator
**没有任何引用** → 随时被 GC;GC 注入 `GeneratorExit` → 它 `finally: await rt.aclose()`
**真的执行** → 检查跑到一半 `runtime._bots` / `runtime._push` 变成 `None`、DB 引擎被 dispose。

表现:`/status` 里没有 `bots` 键(V59 假失败)、`publish_analysis` 报"无绑定群"(V58 假失败)。
**单看业务代码怎么都对**,查了很久。

修法:`_runtime()` 把 context manager 存进 `runtime._extras` 保活。

### 4.2 订阅回执死锁:收帧循环必须在 `subscribe` **之前**起(🔴 客户端)

`_subscribe()` 走 `_send_wait`,而 ack **只能由收帧循环投递**。
原来的 `_serve_once` 先 `await self._subscribe()` 再起 `_recv_loop` →
订阅帧发出去后**没有任何人在读 socket** → 必然 10s 超时 → 判"认证失败" → 重连 → 再超时……
**永远连不上**,而日志只说"等待回执超时",指不到病根。

旧同步实现(`aibot.py:104-109`)里 `_recv_thread` 就是在 `_send_wait` **之前** `start()` 的。
修法:`_serve_once` 先 `create_task(_recv_loop)` 再 `_subscribe()`。

> 这条**只有在"真起一个 WebSocket 服务端"的验收方式下才会暴露** ——
> mock 掉 `BotClient` 的验收永远发现不了它。

### 4.3 `start_bots()` 被懒构建的占位实例短路(🔴 装配)

`Runtime.bots` 是懒构建的:`start_push()` 会先创建一个 `BotManager([])`;
随后 `start_bots()` 原实现写的是"若 `_bots is not None` 就直接返回" →
**永远不从 `core_bots` 读凭据、不注册消息链**,却报告"网关已启动"。

若改成"新建一个再赋值",后果更糟:已经持有旧实例的 `PushService` 会永远对着
一个 0 实例的管理器发消息 —— 每条推送都失败,而且看起来"配置没错"。

修法:新增 `BotManager.add(item)` **就地添加**(实例身份不变)+ `Runtime._bots_started`
标志区分"实例存在"与"已经真正启动";`main.py` 把 `start_bots()` 提到 `start_push()` **之前**
(派发器 worker 数 = 在线机器人数)。

### 4.4 `eval_condition` 的 **`op` 形式** `any_gt` / `or` / `any_below_mean` 恒真(🔴 与 D9 同类)

计划书 §5.6 的 DSL 表与 `alert_rules.json` 的 D/E 规则都用
`{"op":"any_gt","value":0,"fields":[...]}` / `{"op":"or","items":[...]}` 写法,
而 `eval_condition` 只认 `{"any_gt": ...}` 键形式 —— `op` 形式会掉进
「没有 `field` → 返回 `True`」那一行,**恒真**。
后果:E 规则"5 个计数任一 > 0"变成"永远触发";`or` 条件永远通过。

修法:`eval_condition` 同时接受两种写法。**V43 补了正例 + 反例**(只测正例发现不了恒真)。

> 这是 D9 的**第二个实例**,同一类 bug:签名兼容但语义恒真。
> 教训:验收条件 DSL 必须**正例与反例成对**,否则"恒真"会被当成 PASS。

### 4.5 `split_message` 可能产出 **4 条**(违反 A2-6 的 ≤2 条)

原实现在"按店对半"之后又对每个半段做了一次硬切 → 6 店 8709 字会拆成 4 条。
修法:改为"目标 ≤3500,但**≤2 条与不丢内容优先**"的均衡切分(`_balanced_cut`),
并明确写进 docstring:三者不可兼得时**牺牲字数上限**。

### 4.6 段1 遗留:三个批次 D 提取器被当成有参构造调用(🔴 段1 的真 bug)

`jobs.py` / `cli.py` 里写的是 `PortalExtractor(runtime.rules)` /
`RoomExtractor(...)` / `ReviewExtractor(...)`,但这三个类**都没有 `__init__`** →
`TypeError: XXXExtractor() takes no arguments`。

后果:`collect.portal` / `collect.room` / `collect.review` **三条任务整条失败**,
以及 `hoteldata collect portal|room|review` 三条 CLI 命令直接崩。
段1 的 V1–V20 没有覆盖到这三条任务的**实例化**路径,所以一直没暴露。

修法:改为无参构造(3 处 × 2 文件)。

### 4.7 `docs/参考/` 被 lint 扫到(17 条)

那些是**归档的参考证据**(旧系统扫描/复核脚本原文),带着旧系统的
`# -*- coding: utf-8 -*-` 等写法。改了就不再是证据 → 加进 `ruff` 的 `exclude`。

### 4.8 段1 验收器 V12 / V14 因段2 的**有意变更**而红

* **V12** 原断言"恰好注册 9 个任务";段2 §5.9 新增 10 个 → 必然失败。
  改为断言"**段1 的 9 个任务仍全部在册**"(superset 不变式)。
* **V14** 原拿 `ops.selfcheck` 当补跑探针;段2 §5.9 明确把它的 `catch_up` 定为
  **False** → 探针失效。改为注册一个**验收专用的空跑探针任务**
  (`verify2.catchup`,cron `0 6 * * *` / `catch_up=True` / `max_delay=4h`),
  只验"补跑算法"这一条不变式,与业务任务的 cron 解耦。

> 两处都**只改断言、不放宽意图**,并在脚本里写明了改动理由。

### 4.9 `ops.selfcheck` 的 `enabled_flag` 把"可观测性底线"和"可选项"绑在了一起(🟡)

原写法 `enabled_flag="ops_selfcheck_push"` —— 而 `infra/tasks.py::build_scheduler`
遇到 `enabled_flag` 为假会把任务**整个跳过注册**。后果:`OPS_SELFCHECK_PUSH=0`
会连带**自检指标也算不出来、`job_runs` 里也没有记录**,而它自己的 docstring 却写着
"只控制推送那一步,指标照算"。

修法:去掉 `enabled_flag`,推送开关**只在 `selfcheck_push.push_report()` 内部生效**
(关掉 → 返回 `{"pushed": 0, "error": "OPS_SELFCHECK_PUSH=0(推送关闭)"}` 并记日志)。

**实测证据**:`OPS_SELFCHECK_PUSH=0` 时任务仍然在册、`status=ok`、
指标键 `['accounts','checked_at','collect_yesterday','dirs','disk','errors','hotels','interpreter']` 齐全。

### 4.10 `push_daily` 用 `None` 掩盖"装配漏了"(🟡)

`PushService.push_daily` 在 `daily_builder` 未注入(没走 `Runtime.start_push()`)时原来
**返回 `None`**;而命令链把 `None` 解释成"暂无数据" —— 于是
**"装配漏了"被伪装成"这家店今天没数据"**,又是一次静默失败。

修法:返回 `Delivery(ok=False, error="日报组装器未注入(push 未启动)")` + `logger.error`。
「今日数据」现在能回出真实原因。

**实测证据**:未装配 → `Delivery False 日报组装器未注入(push 未启动)`;
`start_push()` 之后 → `daily_builder` 已注入,未绑定群 → `None`(正常的"无数据")。

### 4.11 自检推送文案里有一句**自相矛盾**的话(🟡)

段1 `selfcheck.py` 的 notes 里写着「本模块**只出指标、不推送**:推送是段2 T2G.1 的职责」。
段2 的推送壳会**把这些 notes 原样带进推送文案** → 运维群里收到的消息一边说"我不推送"
一边就是一条推送。

修法:改措辞为「本模块只出指标、不发送;推送由段2 ops.selfcheck 的推送壳完成(T2G.1)」
—— 边界本身没变(**本模块自己**依然一个字节都不发),但这句话在两种上下文里都为真。

### 4.12 另两项**已实测确认无问题**的行为(留证)

* **`AIBOT_ENABLED=0` / `core_bots` 为空** → 推送 `ok=False, error='没有可用的机器人(core_bots 表为空)'`,
  并且**写下一行 `failed` 审计**(`bot_id` 为 `str`)—— 不是静默丢失;
* **`push_daily` 的段3 钩子** → `daily_builder` 注入后,`price_section` 会拼在日报段末
  (计划书 §1.4 指定的位置),段3 只需传参、**不必回头改日报组装代码**。

### 4.13 `alert_logs` 的键:`DO NOTHING` 会让"重推成功"不可见(🔴 交付后评审发现)

> 这一条是**交付后与用户一起评审**时定下来的设计修正,单独记在此处。

**问题**:`write_log` 原来是 `ON CONFLICT (dedup_key) DO NOTHING` 并返回 `None`。
``check(force=True)`` 会绕过触发级去重**真的重发**,但这次重发的结果撞上同一
``(触发×目标)`` 的唯一键后**被丢掉** —— 表里仍留着上一次的 ``failed`` 行。
于是运维看到的是"这条预警一直失败",而它其实早就恢复了。这正是段2 要消灭的
"静默失败"的又一变体。

**修法**(迁移 `0004`):

1. 把键拆成两列,各归其位 —— ``delivery_key``(行身份,UNIQUE)与
   ``trigger_key``(触发身份,普通索引)。后者才是计划书 §5.7 写的「日志去重键」,
   现在可以按触发聚合出"这条预警推给了哪些目标、谁失败了"。
2. 冲突策略由 ``DO NOTHING`` 改为 ``DO UPDATE``:稳态仍是 **1 行/触发×目标**
   (送达率分母不变、依旧准确),但**最后一次投递结果胜出** → 重推的恢复可见。
3. ``write_log`` 返回 :class:`LogWrite`(``id`` + ``created``):区分"新建"与"刷新"。
   ``DO NOTHING`` 时代那个 ``deduped_logs`` 计数器因此失去了含义,已换成
   ``refreshed_logs``(>0 即"这次真的刷了旧行",也就是重推生效的证据)。
   ``created`` 用 ``RETURNING (xmax = 0)`` 判定 —— 这是 PG 的实现细节,但这里
   **只用来给计数器打标**,行的正确性完全由 UNIQUE 索引保证,所以依赖是安全的。

**验收**:V54 现在断言``id`` 不变 + ``created=False`` + 行内容 ``failed→成功`` +
总行数不变 + 同一触发两个收件人共享 ``trigger_key``。

**回填口径**(迁移里写明了):``entity_key`` **可能含冒号**
(``event:中秋节:2026-10-11``),而 ``recipient`` 不含,所以回填只能
**从右往左剥一段**:``regexp_replace(delivery_key, ':[^:]*$', '')``。
本机执行时该表为 0 业务行,但迁移不依赖"恰好为空"。

### 4.14 会"真的发送"的 CLI 命令**没有拉起机器人网关**(🔴 用户提问时查出来的)

**怎么发现的**:被问"我该怎么测试这个功能"时,顺着"用户会敲哪条命令"去核,
发现 `hoteldata push now` 走的是 `await rt.start_push()` —— 而
``Runtime.bots`` 是**懒构建**的,``start_push()`` 只构造 ``PushService`` 并把
当前那个**空** ``BotManager([])`` 塞进去;**只有** ``start_bots()`` 才会去
``core_bots`` 读凭据并 ``add()`` 进同一个实例。

**后果**(实测,插一个假凭据 bot 行):

==================================  ==============  ==================================
装配顺序                              bots.size()     投递结果
==================================  ==============  ==================================
只 ``start_push()``                    **0**          ``(False, '没有可用的机器人(core_bots 表为空)')``
``start_bots()`` + ``start_push()``    **1**          真正去连服务器
==================================  ==============  ==================================

即:**表里明明有机器人,命令却报"core_bots 表为空"** —— 一句谎报原因的报错,
比直接崩还难查。受影响的是全部"会发送"的 CLI:
`push now` / `alert test --send` / `alert summary --push` / `report run` /
`review draft|auto|analysis --push`。

**修法**:CLI 加统一助手 ``_ensure_gateway(rt)``(先 ``start_bots()`` 再
``start_push()``,``core_bots`` 真为空时**只警告不中断** —— 让命令跑完,
由 ``push_logs`` 里那行 ``failed`` 审计如实记录),并在上述每条发送命令里调用;
干跑类命令(`alert test` 不带 `--send`)**不拉网关**,免得白等一次连接。

**防复发**(V59 新增两条守卫):

1. **实例身份不变式**:``rt.push.manager is rt.bots`` 且 ``rt.sender.manager is rt.bots``
   —— 这是整类 bug 的**根因防线**:只要有人"新建一个 BotManager 再赋值",
   这两条立刻红;
2. **CLI 发送命令的源码级守卫**:逐条检查 7 个发送命令的函数体里有没有
   ``_ensure_gateway`` —— 防的是"将来新增一个发送命令时忘了加"。
   (写这条守卫时它先把我自己的函数名解析逻辑抓了出来,改正后才通过。)

## 5.5 验收器自身的一个缺陷:V59 的**locale 依赖**(2026-10-01 修)

**这不是产品缺陷,是 harness 的缺陷** —— 但它曾一度被误读成"产品回归",
所以值得单独记一笔。

### 现象

`_empty_registry_probe` 会**另起一个干净子进程**去验"空注册表 + `with_scheduler=True`
必须报错"。产品侧一直是对的 —— 子进程 `rc=1` 且抛出:

```
RuntimeError: 任务注册表为空,拒绝启动一个 0 任务的调度器(那等于所有定时推送静默失效)。
```

但 V59 **红**:因为验收器用 `encoding="utf-8"` 解码子进程输出,而子进程在
**中文 Windows** 上按 **GBK** 写 → 中文全成 `����ע���Ϊ��` →
`marker in blob` 为假 → 走兜底分支返回最后一行 → `scheduler_refuses_empty=False`。

### 实测数据(`scripts/diag_v59_flaky.py`,同一探针固定条件重复跑)

| 条件 | 子进程 stdout 编码 | utf-8 解码命中标记 | 结果 |
|---|---|---|---|
| 不传 `env`(父进程也没设 `PYTHONIOENCODING`) | `gbk` | **0 / 6** | V59 **稳定红** |
| 传 `env={"PYTHONIOENCODING": "utf-8"}` | `utf-8` | **3 / 3** | V59 **稳定绿** |

### 为什么这个 bug 特别容易误判

它**不是随机 flaky,而是环境依赖的确定性行为**:

* 父进程环境里恰好有 `PYTHONIOENCODING=utf-8`(某些终端 / CI / 手工 `export`)→ V59 **稳定绿**;
* 没有 → V59 **稳定红**。

于是它表现为"换台机器 / 换个 shell 就变",极易被当成"偶发"或"产品回归"——
**两者都不是**。本项目就发生过一次:维护者每次手工跑验收前都先 `export PYTHONIOENCODING=utf-8`,
于是**无意中把这条断言"环境合规化"了**,一直看到 39/0,直到在干净会话里才复现 38/1。

### 修法(一行)

```python
env={**os.environ, "PYTHONIOENCODING": "utf-8"},
```

修完在**不设** `PYTHONIOENCODING` 的干净环境下连跑 3 次:全部
**39 PASS / 0 FAIL / 1 BLOCKED**。

### 顺带查过

`scripts/` 下只有这一处"读外部子进程输出";`check_admin_web.py` 也起子进程,
但它只通过 HTTP 与之交互(不读它的 stdout),且已传同样的 env,无此问题。

| **`alert_logs` 的键设计** | **正式设计(不再是"有意偏差")** | 迁移 `0004` 把键拆成两列:``delivery_key``(行身份,``rule:hotel:entity:date:recipient``,**UNIQUE**)与 ``trigger_key``(触发身份,``rule:hotel:entity:date``,普通索引)。<br>**为什么行必须带收件人**:计划书 §5.7 自己把送达率定义成「成功行 ÷ 总行;无管理群也要计入分母(写 ``recipient='manage-none'``)」—— ``manage-none`` 是一个**收件人值**。若一行代表一个触发,那条"推 3 个目标只留 1 行"的记录写 ``true`` 会让 B/C 的失败在日志里消失(D1 同类),写 ``false`` 会抹掉 A 的成功并低估分母,**没有第三种写法**。<br>**为什么行身份那列不叫 `dedup_key`**:真正的当日去重是**触发级**的,由 ``alert_states.should_push`` 承担;拼上 recipient 之后"去重键"这个名字就在说谎。``trigger_key`` 才是计划书里那个「日志去重键」,现在是一等公民、可聚合。<br>**为什么冲突策略是 UPSERT 而非 DO NOTHING**:``check(force=True)`` 的重发会被 DO NOTHING 丢掉 → 表里留着旧的 ``failed`` 行,运维看到"一直失败"而实际早已恢复。改成 ``DO UPDATE``(最后一次结果胜出)后:稳态仍是 **1 行/触发×目标**(分母准确)、**重推的恢复可见**、逐目标失败照旧留痕(V54 专测:`id` 不变 + ``created=False`` + 行内容 ``failed→成功`` + ``trigger_key`` 聚合出 2 个目标) |
| **`draft_md` 格式** | 逐字照旧 | 用旧 `review_reply.py` 的 6 行格式(而非计划书任务书里的单行示例) |
