## 0. 一句话总结:计划书对旧系统的诊断"轻了"

计划书 §4.4 把 D13(`distance_km` 恒 `None`)定为段3 的头号必修项,并把段3 核心价值概括为
「旧系统唯一写了距离排序,但距离是空的」。

实测比这严重得多。旧比价域的真实状态是:

> **取价语义已经崩坏**(12/18 条把优惠券当房价),**兜底被券价挡住而永不触发**,
> **跨平台比价被自己合并掉了**(`_merge_quotes` 把两个平台价压成一条,只留先到的那个),
> **距离/视觉/截图/单店定时四条能力全部零生效**,**生产端到端只成功跑通过一次**
> (`push_logs` 全表仅 1 行 `price_compare`)。

「距离是空的」只是四个病里最显眼的一个。**若段3 只修距离,会把「券当房价」原样搬进新系统。**

## 1. 🔴 关键修订(3 处)

### P1 · D13 范围升级:从「修距离排序」到「取价语义 + 距离」双核心

| | 计划书原文 | 实测 |
|---|---|---|
| §5.6 | 「接口命中则**零点击**取价」 | `ctrip.py:82-108` 的 `_scan_hotel_entries` 要求条目里有 **≥2 个数值型 price 键**;真接口 `data.hotelList[]` 里**没有数值型 price**(旧 diag 只存了 4000 字预览,可见部分无价格键)→ **捕获链路必然失效,"零点击直连"从未生效** |
| §4.4 | 「`price_source` 正确标注」 | 旧系统 `price_source` 只有 `"DOM"/""` 两个值,**接口价与券价都被标成 DOM**;下游 `report.py` 根本不渲染它 |
| —— | —— | 实测 18 条归档:**4 条真酒店 / 12 条券价假阳性 / 2 条 0 家** |

**根因**:取价走的是启发式 `parse_price`(`prices.py:24-51`,5~100000、取 min、排除 1000–2999 整数),
于是「折扣券 ¥34」「十亿豪补 ¥12」成了"房价";而兜底条件是
`if not hotels or all(price is None)`(`ctrip.py:343`)—— **券价让它恒为假,「显示地图」兜底整段跳过**。

**修订**

1. 契约 `HotelQuote` 增加 **`price_scope: Literal["from","exact"]`**,区分「起价」与「确定价」;
2. 增加 **`price_rejected: list[str]`**(或在 `raw` 里留 `rejected`),记录被**券价过滤器**丢掉的候选 —— **丢弃要可见,不许静默**;
3. 券价过滤规则集中一处(券/红包/立减/补贴/豪补/返现 → 丢弃),不散落在启发式里;
4. **§5.6 的表述改为「接口保证 名称/ID/坐标;价格优先接口、取不到降级 DOM」** ——
   把"接口能不能给价"降级为**待实测项**(需真机录一次完整响应),而不是写死成设计承诺;
5. 兜底触发条件改为「**没有可用报价**(`not quotes` 或全部 `price is None` **且无 price_rejected** 之外的候选)」,不再被脏候选挡住。

> **坐标才是接口能保证的东西** —— `position.lat`/`position.lng` 已在真响应中确证存在。

### P2 · V73「房型粒度」按列表页做不到 → 接受「起价」+ 显式标注

实测:两个平台的列表页**只给「起价」**(携程 DOM / 美团 `em.poi-price-num`),
**旧系统房型名/房型价完全未实现**(`room_type` 只进报告头)。真房型价必须**逐家打开详情页**。

**修订**(已确认)

* 列表页取「起价」,`price_scope="from"` **显式标注**;报告与库中都诚实标注口径;
* **V73 改为「起价口径正确」**:按 `PRICE_QUOTE_COUNT`(1~3)取**报价条数**,并断言
  `price_scope` 落库正确;
* 房型粒度**延后**,列为段3 之后的候选(届时需重估单店耗时与风控预算)。

### P3 · §1.3/§4.1/§5.7 严重失实:`human`/`geo` 段1 **根本没迁**

| 计划书原文 | 实测 |
|---|---|
| §1.3「真人操作节奏 → 复用自 段1 已迁入的 `human` 模块」 | `glob` 全仓 **无** `human.py`;`README` §7.7 只把「真人节奏库」列为段1 的**目标**,从未落地 |
| §5.7「段1 已把 `human` 迁入共享位置;段3 **直接复用,不复制**」 | 同上 |
| §4.2「`comparator/human.py` 全套 ✅留」 | 留 = 段3 **自己搬** |

**修订**(实测结论)

1. 段3 **自己移植** `human.py`(228 行)+ `geo.py`(92 行),落点 `domains/compare/human.py` 与 `domains/compare/geo.py`
   (与 §5.1 目录结构一致);
2. **异步化**:`time.sleep` → `asyncio.sleep`(旧 `human.py` 是同步 API,新系统是 async Playwright);
3. **`geo` 必须改造**:旧 `deep_find_coords` 返回**扁平列表 `list[(lat,lng)]`,无法与酒店逐条对齐**
   —— 这是旧系统"抓到了坐标却接不上线"的技术原因。新实现改为**逐酒店坐标提取**
   (从 `position.lat`/`position.lng` 成对取,或卡片文本 `positionDescOfCtrip` 兜底);
4. `HAVERSINE_R = 6371.0088` 与 `norm_hotel_name` 三步归一化**逐字继承**。

### P3b · 附:`_merge_quotes` 的语义必须反转(计划书未识别)

`runner.py:85-115` 把**跨平台同名酒店合并成一条**,且 `if old.get("price") is None`
—— **只保留先到的那个平台价,第二个平台的价被丢弃**。这与"比价"的语义**正好相反**。

**修订**:新系统的**跨平台合并只用于归一化去重与展示分组,绝不合并价格**。
同一家酒店在携程 / 美团各自的报价**必须都保留** —— 这正是"比价"的产出物本身。

## 2. 🟡 设计漏洞(6 处:照计划书写会写出死配置或断层)

### P4 · `HOTEL_BATCH_HEADLESS` 无法生效 → 删

`infra/browser.py:146/158` 的 `headless` 是 **Chromium 进程级**(`launch(headless=...)`),
不是 context 级(`_new_context` 不设 headless,`ContextSlot.headless` 只是记录 `cfg.headless`)。
**一个 `BrowserPool` 只有一个 headless**,「交互有头 + 批量无头」在一进程内不可共存。

**修订**(已确认):**只保留 `HOTEL_HEADLESS` 一个开关**(比价全程可配),删除 `HOTEL_BATCH_HEADLESS`。
理由:定时任务跑在 `serve` 进程里,天然与交互式 CLI 分离,实际不影响使用。

### P5 · 附录 A 漏了 4 个旧配置

| 项 | 旧系统默认 | 为什么该留 |
|---|---|---|
| `HOTEL_TOP_N_OPEN` | `6` | **坐标缺失时逐个打开候选页的上限** —— 与新兜底路径直接相关(注:编排层考古判定其业务引用数为 0,属"半死";建议以 `HOTEL_COORD_FALLBACK_MAX` 之名复活并**真正接线**) |
| `HOTEL_BATCH_PUSH` | `0`(旧 `.env` 实设 `1`) | 批量跑完推汇总 |
| `VISION_PROVIDER` | `zhipu` | 供应商切换(计划书只列了 ZHIPU) |
| `HOTEL_BATCH_LIST_LEGACY` | `hotels.txt` | 旧名兼容(导入脚本一并读) |

### P6 · §5.8 建表 SQL 与 §5.9 自相矛盾 + 键设计断层

| 问题 | 说明 |
|---|---|
| **`is_demo` 列不存在** | §5.9 要求「演示数据隔离 → 显式列 `is_demo`,不用 LIKE 猜」,但 §5.8 的 `cmp_price_comparisons` 建表语句里**没有这一列** |
| **`anchor_name` 文本作键** | §1.4 钩子是 `build_price_section(hotel_id, date)`,但表按 `anchor_name` 存 → 必须反查 `core_hotels.name`,**酒店改名即失联** |
| **§5.9 的"非演示来源"无法判定** | `should_run_batch` 要判"今天有没有真数据",而没有 `is_demo` 就判不了 |

**修订**:`cmp_price_comparisons` 补 **`hotel_id bigint`(可空,回填历史/宽松关联)** 与
**`is_demo boolean not null default false`**;`should_run_batch` 按 `is_demo = false` 判。

### P7 · §1.4 钩子签名与段2 既成事实对不上(段3 要补一层)

* 计划书写:`build_price_section(hotel_id, date) -> str | None`(**按店**)
* 段2 已落地:`daily_builder(chatid, price_section)` —— **一个群一个字符串**(`runtime.py:351-357`)

一群多店时,需要**群级组装器**把 N 家店的段拼起来。

**修订**:段3 交付**两个**函数,**段2 代码一行不改**(钩子已在 `daily.py:199`):

```python
async def build_price_section(hotel_id: int, day: date) -> str | None:   # 单店
async def build_group_price_section(chatid: str, day: date) -> str | None:  # 群级(N 店拼接)
```

> ★ 旧系统**已经解决过这个问题**:`compare_md_for_groups(hotel_names, ...)`
> (`app/price_push.py:126-132`)= 首行 `📊 **比价汇总**（{n} 家酒店）` + 逐店段 `\n\n` 拼接。
> **逐字继承这个形状**,只是数据源从 SQLite 换成 PG。

### P8 · slot 映射未定

采集槽是 `08:30/13:30/17:30`,而 §1.4 说「返回当日 **09:00** slot 的比价段」——
**09:00 不对应任何采集点**。

**修订**:明确钩子语义为「**取当日最近一个已完成的 slot**」(默认最近),
CLI 提供 `--slot` 覆盖;报告与推送文案里**显示该 slot 的实际时刻**,避免"看起来是实时价"的误导。

### P9 · V82「段2 代码未被修改」无法用 git 验证

`hotel-data-system/` **不是 git 仓库**(`git rev-parse` 失败)。
V82 的"段2 代码一行未改"必须改用**文件哈希基线**:开工前对
`domains/report/daily.py` / `push/service.py` / `runtime.py` 等取 SHA256 存档,
验收时比对。
