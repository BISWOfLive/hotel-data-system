# 段2「企业微信推送」联调测试指南

> 给**人**看的手把手测试步骤。验收器(`scripts/verify_acceptance2.py`)跑的是
> 自动化断言;本文档回答的是"我自己怎么把这个功能摸一遍"。

分三层,**按顺序做**:

| 层 | 需要什么 | 耗时 | 覆盖 |
|---|---|---|---|
| **① 离线自测** | 只要 PG 起着 | ~5 分钟 | 配置资产 / 任务表 / 22 项排期 / **V21–V60 全量验收** |
| **② 真实企微群联调** | 一个企微智能机器人的 `bot_id` + `secret` + 一个测试群 | ~20 分钟 | 长连接 / 群命令 / 日报 / 预警 / 审计 |
| **③ 缺陷逐条复现** | 同上 | ~10 分钟 | D1 / D5 / D9 / D10 / D17 / D18 |

## ① 离线自测(不需要任何凭据)

### 0. 前置

```bash
docker compose up -d pg                    # PostgreSQL 16(端口 5433)
poetry run alembic upgrade head            # 0001 → 0002 → 0003 → 0004
```

### 1. 环境与配置资产自检

```bash
poetry run hoteldata env
```

逐项看这几行(**必需项缺失会红、段2 资产缺失会黄**):

```
✓ [必需] api_rules.json: 存在
✓ [必需] push_rotation.json: 存在
✓ [段2] report_schedule.json: 存在
✓ [段2] alert_rules.json / alert_shots.json / alert_lines.json: 存在
✓ [段2] review_templates.json / review_sources.json: 存在
✓ [段2] prompts/*.md: 10 个模板
✓ [段2] knowledge/faq.json: 存在
! MANAGE_CHATIDS 为空 → 11 条管理群命令**一律拒绝**(这是有意的安全默认,不是 bug)
```

最后那行 `!` 是**预期的**——没配管理群白名单时管理命令拒绝服务。

### 2. 任务表(时刻表的唯一来源)

```bash
poetry run hoteldata task ls
```

应看到 **19 个任务**,其中段2 的 11 个重点核对:

| 任务 | cron | 补跑 |
|---|---|---|
| `push.daily` / `push.schedule` | `0 9 * * *` | 是 |
| `alert.room` | **`4 9,14,19 * * *`** ← 错峰 +4 分钟 | 是 |
| `alert.data` | `10 9 * * *` | 是 |
| `alert.summary` | `30 9 * * *` | **否** |
| `review.suggest` / `review.analysis` / `review.auto` | `50 8` / `0 9` / `40 9` | 是 |
| `review.realtime` | `0 8-23 * * *` | **否** |
| `ops.violation` | `0 * * * *` | **否** |

> `alert.room` 的 cron 是 **09:04 / 14:34 / 19:04**,而规则里写的是
> **09:00 / 14:30 / 19:00** —— 这就是"两层时刻结构",**不是笔误**。

### 3. 22 项排期

```bash
poetry run hoteldata report ls                # 今天
poetry run hoteldata report ls --date 2026-10-05   # 挑个周一看 monday 桶
```

核对:列出 22 项;周三只有 `daily` 桶的 19 项;"仅周期桶"的
`svc_weekly` / `svc_compare` / `peer_compare` 显示 `(今日不发)`。

### 4. ★ 全量验收(V21–V60)

```bash
poetry run python scripts/verify_acceptance2.py            # ~2 分钟
poetry run python scripts/verify_acceptance2.py --only V35 V36 V37
poetry run python scripts/verify_acceptance2.py --no-cleanup   # 保留合成数据便于翻库
```

## ② 真实企微群联调

### 1. 加机器人

```bash
poetry run hoteldata bots add --name bot01 --bot-id <企微bot_id> --secret <企微secret>
poetry run hoteldata bots list          # 只显示名字/状态/容量,不回显凭据
```

凭据用 Fernet 加密后落库,**明文不落盘**。

### 2. ★ 先单独验连接(别急着起服务)

```bash
poetry run hoteldata bots health --wait 5
```

```
bot01            在线
在线 1 / 1
```

这一条**最关键**:它把"协议能不能连上"与"业务逻辑对不对"彻底分开。
如果这里是 `离线`,后面所有推送都会失败,先解决连接问题(见 §④ 排错表)。

### 3. 配管理群 + 绑店

```bash
# .env 里加(逗号分隔):
#   MANAGE_CHATIDS=<管理群chatid>
#   OPS_CHATID=<运维告警群chatid>

poetry run hoteldata bind add --group <群chatid> --hotel <酒店名>
poetry run hoteldata bind list
```

### 4. 起服务

```bash
poetry run hoteldata serve
```

启动顺序是**机器人网关 → 推送派发器 → 调度器 → 补跑**。看日志:

```
机器人网关已启动:1 个实例 ['bot01']
推送派发器已启动:1 个 worker        ← worker 数 = max(1, 在线机器人数)
已注册任务 19 个
```

### 5. 群内命令(在测试群里发)

| 发什么 | 期待 |
|---|---|
| `帮助` | 19 行命令帮助(逐字继承旧系统) |
| `绑定 <酒店名>` | `✅ 本群已绑定:<名>(共1家)`;再发一次是幂等的 |
| `我的酒店` | 列出本群绑定 |
| `状态` | **管理群才可用**;非管理群回 `⛔ 该命令仅管理群可用` |
| `今日数据` | 触发一次日报推送并回执结果 |
| `重推` | 同上,且**绕过当日去重** |
| `离店` | 实时问答(问才发,不参与定时推送) |
| `完全无关的话` | 只回兜底文案,**不触发任何推送** |

### 6. 手动推一条日报并查审计

```bash
poetry run hoteldata push now --group <群chatid> --force
poetry run hoteldata push log --today --group <群chatid>
```

`push now` 会真的发一条日报到群里(标题行 + 当日轮换图 ≤5 张)。
审计表应出现 `status=ok` 的行;`--force` 去掉再跑一次 → 出现一行 `skipped`
(**去重也留痕,不静默**)。

### 7. 22 项报告单跑

```bash
poetry run hoteldata report run flow_overview        # 挑一个带配图的项
poetry run hoteldata report run svc_weekly           # 周报,验"上期对比列"
```

`svc_weekly` 的消息里应看到四列表头 `| 指标 | 本期 | 上期 | 环比 |` 和 🟢/🔴
—— 这是 D10 的修复点。

### 8. 预警联调

```bash
# 先干跑(不发送、不写状态、不写日志)——
poetry run hoteldata alert test --slot 09:00
poetry run hoteldata alert test --rule room_closed_7d --hotel <酒店名>

# 确认真要发时再加 --send
poetry run hoteldata alert test --slot 09:00 --send

# 状态 / 汇总
poetry run hoteldata alert status --hotel <酒店名>
poetry run hoteldata alert summary                   # 只算不推
poetry run hoteldata alert summary --push            # 真推管理群
```

**验"重推恢复可见"**(就是我们刚改的 `alert_logs` 键设计):

```bash
poetry run hoteldata alert test --slot 09:00 --send            # 第一次:建行
poetry run hoteldata alert test --slot 09:00 --send --force    # 重推:应是**刷新同一行**
```

然后查库:

```sql
select id, recipient, pushed, error, delivery_key, trigger_key
  from alert_logs where log_date = current_date order by id desc limit 10;
```

要看的三件事:
1. 同一 `触发×收件人` **`id` 不变**(没有新增行);
2. `pushed` / `error` 被**刷成最后一次结果**(失败→成功可见);
3. 同一触发的多个目标**共享同一个 `trigger_key`**,`delivery_key` 是它的前缀 + `:收件人`。

送达率公式:`select count(*) filter (where pushed) || ' / ' || count(*) from alert_logs where log_date = current_date;`

### 9. 点评联调

```bash
poetry run hoteldata review status                   # 待回复 / 审计分布 / ★门控原因
poetry run hoteldata review draft                    # 只算不推
poetry run hoteldata review draft --push             # 草稿推管理群
poetry run hoteldata review auto                     # 自动回复
```

`review status` 里会明确显示:

```
通道:未就绪 — submit.ready=false(回复提交接口未捕获,见 docs/回复通道研究结论.md §4)
```

**这是已知边界,不是 bug**:回复的提交接口从未被捕获 → 自动回复**必然**走
"未就绪 → 进人工队列"。要验的是它**没有伪造成功**:跑 `review auto --push` 后,
`review status` 的"已回复"应为 0,待回复数不变。

### 10. 清理

第 ① 层验收会自己清理;`--no-cleanup` 跑过的话手动清:

```sql
delete from push_logs    where group_chatid like 'verify2-%';
delete from alert_logs   where rule_id like 'verify2%';
delete from core_group_bindings where chatid like 'verify2-%';
delete from core_hotels  where name like '验收2-%';
```

## ③ 六个旧缺陷:怎么亲手复现"已修"

| 缺陷 | 手动复现法 | 修复后的现象 |
|---|---|---|
| **D1** 告警静默丢失 | 配 **2 个以上**机器人 → `bots health` 确认至少 1 个在线 → 触发一次运维告警(如 `ops.selfcheck` 推运维群:`task run ops.selfcheck`) | 告警**真的发到群里**;日志里是"告警已推送 → <chatid> (机器人 X)"。旧系统在 `set_bot(None)` 时恒返回 False,只留一行 warning |
| **D5** 限频键错 | 验收 `--only V35`(10 个不同群 × 3 worker 实测最小间隔) | 最小相邻间隔 ≥ 配置值;**同一机器人的不同群也受限**(旧系统按 chatid 限频 → 换群就是"零等待") |
| **D9** 条件 `in` 不可达 | `--only V43` | 反例 `lead_days=5` → **False**;旧系统这里恒真 |
| **D10** 周报无环比 | `hoteldata report run svc_weekly` | 消息里有「上期」列与 🟢/🔴 |
| **D17** `bot_id` 类型 | `push log --today` 看 robot 列;或 `select distinct pg_typeof(bot_id) from push_logs;` | 列类型 = `text`,且**按机器人名可统计** |
| **D18** 健康字段读错 | 多机器人下在管理群发 `状态` | 显示的在线数与 `bots health` **一致** |

## ④ 排错速查表

| 症状 | 大概率原因 | 怎么办 |
|---|---|---|
| `bots health` 全是"离线" | 凭据错 / 外网不通 / 机器人未在企微侧启用 | 核对 `bot_id`+`secret`;看日志里 `aibot_subscribe` 回执的 `errcode` |
| 群里发消息没反应 | 服务没起 / 网关没连上 | 先 `bots health`;再看 `serve` 日志有没有"订阅成功" |
| `push now` 报 **"没有可用的机器人(core_bots 表为空)"** | **`core_bots` 真的空**,或用了没拉网关的旧二进制 | `bots list` 确认有行;这条报错**不会**在表里有机器人时出现(§4.14 已修) |
| 推了但群里没有 | 机器人不在那个群 / `chatid` 填错 | `push log` 看 `status`:`failed` 且 `error` 会写清原因 |
| 日报没有图 | 当日截图没跑,或该项缺图被**有意跳过** | 先 `collect --screenshot`;缺图是"跳过 + 管理群告警",不是报错 |
| 预警一条都不触发 | `ALERT_ENABLED=0`,或该时刻无匹配规则 | `alert test --slot 09:00` 干跑看 `rules_checked`;查 `.env` |
| 预警重复推 | 用了 `--force`,或 `dedup` 非 `once_per_day` | `alert status` 看 `last_trigger_date` |
| `状态` 命令说"仅管理群可用" | `MANAGE_CHATIDS` 没配这个群 | 这是**有意**的安全默认,不是 bug |
| 点评永远"未就绪" | `submit.ready=false`(**当前必然**) | 已知边界;用「建议模式」:草稿推管理群 → 人工确认 |

---

## ⑤ 一句话总结

* **想验"代码对不对"** → 跑 `verify_acceptance2.py`,39/40 离线可验;
* **想验"真能推到群里"** → 只需 `bots health`(连接)+ `push now`(投递)+ `push log`(审计)三步;
* **想验"某条旧缺陷修没修"** → 按 §③ 的表逐条点。

> ⚠️ 第 ② 层的每一条我都**没有在真机上跑过**(本机没有企微凭据)。
> 协议层(帧 / ack / 心跳判死 / 分片 / 迟到回执)是用本地 WebSocket 服务端
> **真跑**的,但"真实企微服务器是否接受这套帧"仍然是唯一未验项(V21 BLOCKED)。
